# 文档结构与写作

## 面向读者

读者是接手人工制作、修复、复核或工程接入的人。文档必须让读者不依赖原对话就能回答：做什么、为什么、用什么输入、输出什么、怎样验收、卡在哪里、完成后交到哪里。

## 固定章节

1. **文档用途与当前结论**：章节、revision、完整范围、人工任务总数、主要阻塞及“非正式 PASS”声明。
2. **范围与来源快照**：Item/场景/附属项/排除项数量、活动范围哈希、来源清单和冲突处理。
3. **分类总表**：先按资产性质统计并列出 ID，再按取得路线统计；明确两轴独立。
4. **人工处理总清单**：按“已就绪且可执行 → 被事实／来源阻塞 → 等待回流 → 已完成待复核”排序。
5. **逐场景、逐道具明细**：每个 item/state 一行或一组，保持相同列顺序。
6. **附属玩法与范围外历史**：小游戏、案件板、演出组件、旧容器及历史件单列，解释为什么不进入普通角色。
7. **状态、缺口和后续使用**：候选、provisional、有效 PASS、正式发布与工程接入分列。
8. **可追溯来源**：来源路径、版本／revision、SHA-256；机器 JSON 的过程路径只在需要时列出。

## 明细表列

建议列顺序：

1. Item ID / 名称 / 状态；
2. 资产性质 / 是否照片线索；
3. 取得路线 / 实际事件；
4. 所属场景与容器／演出关系；
5. 必需产物与规格；
6. 当前已有资产与状态；
7. 人工操作；
8. 输入与输出；
9. 验收条件；
10. 阻塞、依赖与返回位置。

列多时使用横向页面或拆成“需求与路线”“人工执行与验收”两张同序表，不把字体压到难以阅读。跨页表重复表头；同一 item 的关键说明不拆散到没有上下文的下一页。

## 人工任务写法

用可执行动词开头，例如“从批准场景原图提取……”“依据当前剧情原文补齐……”“在原生分辨率测量并登记……”。每项包含：

- `输入`：精确文件／来源及版本；
- `操作`：允许改变什么、必须保护什么；
- `输出`：文件角色、尺寸、格式、命名与数量；
- `验收`：视觉、技术、语义、父图／重建、坐标和交接条件；
- `阻塞`：当前不能执行的具体原因；
- `回流`：人工完成后由哪个阶段复核，不能从修改时间推断完成。

避免“优化一下”“按要求处理”“补齐图片”这类无法验收的描述。未知内容写“未决事实 + 来源冲突 + 受影响角色”，不擅自补成确定要求。

## 视觉样式

使用 `assets/document-profile.zh-CN.json`：黑色标题、深蓝表头、浅灰／浅蓝交替行、浅灰边框、表格单元格留足内边距。第一页先给范围和结论，避免装饰性封面。不要用文本框或彩色卡片承载正文。
