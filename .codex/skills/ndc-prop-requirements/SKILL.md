# NDC 道具需求整理

这是五阶段的第一阶段。全批次请求从这里建立内容档案与进度，再依次交接；仅统计请求在这里结束，不能自动进入生图。

先读[共用批次协议](references/batch-contract.md)，再按需读[来源与分类细则](references/production-details.md)。来源顺序遵从项目底层规则；源文件只读，过程产物进入项目工作过程目录。

## 工作步骤

1. 锁定用户范围、章节、编号和场景；核对 canon_manifest.json（项目存在且涉及章节编号时）。按项目来源顺序查找同编号、同状态资产；命中来源后不去后续根目录另选替代品。过程历史可用于恢复批准和拒收证据。
2. 读取相关证据表、场景状态、必要取得节点及现有资产，不全盘加载无关剧情。区别自动授予、场景点击、容器内点击和环境观察；不要因 mapSpritePath 为空就认定无需热区。
3. 形成唯一 content_archive.json。逐项记录原文出处、A类硬要求、B类允许偏差和C类美术自由。年龄、日期、案号、数量、指定状态以及图像玩法所需笔迹先交叉核对；已知事实不得自拟。
4. 以物品身份和状态建立复用关系。同一张内容母版可供多个场景引用；不同光线、角度不自动成为新身份。记录每一场景、菜单、母版和交付角色之间的依赖；按[场景放行合同](references/scene-release-contract.md)覆盖全量场景成员及有来源的跨场景／同物状态／容器／照片内容关联。未知外部关联明确记unresolved，不省略为“无关联”。
5. 把人物手持、递交、开柜转译成无人物的可信物品状态；保留身份、状态、承托和取得顺序。不把角色身高、白模和人物入景作为道具前置。
6. 建立 batch.json、固定 jobs 和产物表。实际取得方式决定 Map/Big/Icon/Type6/Type7 需求；程序未接入另列 integration_status，不能凭空增加美术角色。未锁定事实仅阻断相关依赖。
7. 核对内容档案与完整批次范围，标记第一阶段完成。先init锁定批次，再用migrate-scene-release追加已核对的全范围场景索引；旧批接续保留日志和次数，不再次init。调用共用校验通过后，按授权进入[物品母版制作](../ndc-prop-master-production/SKILL.md)；某场景全部关联前置已齐即可进入第三阶段，无需等待无关场景母版。

## 既有资产查验的固定位置

识别编号／类别／状态 → **检索既有资产并核对角色缺口及已有审核依据** → 补全内容与关联 → 锁定档案 → 先补缺。此处是避免重复生产的必要盘点，不要求先重新视觉审完所有旧图；全面复检和旧问题重制遵从[执行优先级](references/batch-contract.md#执行优先级与清单授权)。已授权任务自行核对清单后生产，不等待用户审批。

每件在content_archive.json的inventory内记录关键词、已查根目录及命中、命中图的完整路径／SHA-256、审核和拒收出处、缺少的角色／状态，以及一个disposition：reuse、complete_missing、repair、regenerate、new、blocked。found与usable分别判定：已有PNG不等于当前可复用；有合格Big但缺Map应补缺角色，不重生Big。跨场景／跨状态逐个比对，命中后停止另选后续来源，仅补查相关历史审核证据。

后面阶段检查所引用的路径、字节、需求和拒收是否变化；没有变化不重做全盘检索。发现缺失／变更时只回补相关inventory条目。

## 接续与变更

以用户最新有效指令校正批次 objective、current_stage、next_action，再恢复当前拒收和进度；当前“仅统计／暂停”必须遵守，已经被用户明确恢复生产的旧暂停不再沿用。不要重新扫描所有历史目录。来源变化只修正相关档案并撤销受影响派生。历史接入区分未开始、已知次数和未知占用，遵从共用协议，不将换Skill当作重置次数。
